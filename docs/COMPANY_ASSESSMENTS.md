# Company assessments

Proctored mock assessments for every company in
`Ques/50 Companies Steps Assessment Research.docx`, built from the 11-section
master question bank in `Ques/`. Students find them on the student dashboard
(grouped by company tag) and at `/company-assessments`. **Each student gets one
attempt per company.**

## At a glance

| | |
|---|---|
| Companies | 60 — the union of the document's prioritised target list and its 50 step sections (see *Company list* below) |
| Tags | IT Services & Consulting (15) · Global Product & Big Tech (15) · Indian Product Companies & Startups (17) · SaaS & Developer Tools (6) · Banking & Financial Services (4) · Semiconductors & Engineering (3) |
| Question bank | 1,189 validated items: every unique Ques question + reviewed supplements, generated quant, 159 DSA MCQs (hard is the largest band) and 43 LeetCode-style coding problems (21 medium, 22 hard; 379 hidden tests incl. 73 stress tests) |
| Question types | MCQ (server-scored), written answers (rubric / LLM grader), coding (LeetCode-style judge: hidden + stress tests with per-test time limits, Python 3 or JavaScript) |
| Duration | 100–120 minutes per company, one server-side timer |
| Proctoring | Same protections as the original assessments (see below) |

## How a company mock is composed

1. **Hiring steps** come verbatim from the research document
   (`lib/company/generated/researchSteps.ts`, generated by the bank build).
2. A **blueprint** (`lib/company/blueprints.ts`) turns the assessable steps into
   rounds. Each round references its step number and draws questions from the
   sections that step describes — e.g. TCS *Step 2: Foundation Assessment —
   Numerical, Verbal and Reasoning Ability* → Section 1 by area; Google *Step 5:
   Design Round* → Sections 8 and 9. Eligibility and final-selection steps are
   informational only.
3. At **start**, `lib/company/paper.ts` builds the paper from the blueprint with a
   per-student seed: difficulty mix per part, round-robin spread over sections
   and topics, no repeated question or question group, easy → hard ordering,
   options shuffled per attempt.

| Blueprint | Companies |
|---|---|
| `tcs`, `infosys`, `wipro`, `cognizant`, `accenture` | the five IT-services companies with documented flows |
| `service` / `service-digital` | the other IT-services targets (modelled flow, marked *not documented*) |
| `product`, `product-lp`, `product-systems`, `product-enterprise`, `product-devtools` | big tech, product and dev-tools companies (product template in the document) |
| `startup`, `startup-fintech` | startups using the document's startup template |
| `bfsi` | Goldman Sachs, Morgan Stanley, JP Morgan, HSBC (includes the *Domain / Business* round) |
| `engineering` | Siemens, Bosch |

To **add or hide a company**, edit `SEEDS` in `lib/company/catalog.ts` (name,
slug, tag, blueprint, track). Tests guarantee every blueprint remains
satisfiable from the bank.

## The question bank

```bash
npm run build:company-bank   # Ques/*.docx + supplements → data/company/bank.json
npm run verify:company-bank  # executes every computed answer key
```

The build is deterministic (content-derived ids), so in-flight attempts keep
resolving their questions after a rebuild. `data/company/bank-report.json`
records counts per section and every correction applied to source items.

### What the Ques documents actually contain

The documents claim 3,000 questions, but they were generated by repeating a
small set of items with suffixes such as "(Variant 12)" / "(Question 7)":

| Section | Claimed | Unique | Notes |
|---|---|---|---|
| 1 Aptitude | 450 | 215 | 6 numeric templates; synonyms, antonyms, grammar, RC, syllogism, coding-decoding and directions are **one question each** repeated 30× |
| 2 Programming | 250 | 38 | |
| 3 DSA | 700 | 23 | one question per topic, repeated ~30× |
| 4–11 | 150–350 each | 30 each | 15 open-ended prompts × (plain + one fixed "angle") |

The documents also state *"No answer key is included"*. The build therefore:

- **de-duplicates** everything (each bank item keeps its `sourceRefs`),
- **re-derives the answer key** of every templated item by computation — this
  caught **4 wrong implied keys** (ratio items #117–#120 ask for the smaller
  share but option A is the larger), 6 ill-posed items (ratio *n:n* "smaller
  quantity", re-asked as "each quantity"), 3 duplicate-option items and a
  syllogism whose key merely restated a premise — all logged in the report,
- **calibrates difficulty by content**: the documents label items by position
  (identical text appears as Easy, Medium and Hard); the original label is kept
  as `sourceDifficulty`,
- adds **supplements** (`data/company/supplements/*.json`) so every section has
  a real pool: verbal/reasoning/finance aptitude, output-prediction and
  pseudocode, DSA analysis, objective MCQs for sections 4–10, written
  communication prompts, and 43 coding problems. Every computed key
  (code output, SQL results, arithmetic) is **executed** by
  `verify:company-bank`; coding reference solutions are run through the real
  harness by the test suite in both languages,
- attaches a **rubric** (5–6 key concepts) to every open-ended prompt
  (`supplements/rubrics.json`).

## One attempt per student per company

Enforced on the server, never trusted to the browser:

- The attempt id is derived from `(student, company)`; the paper seed from
  `(student, company, server secret)` — racing requests converge on one row
  and one paper.
- `POST /start` returns the existing attempt (resume, same paper and deadline)
  or **409** once it is submitted/expired.
- Supabase: `UNIQUE (student_id, company_slug)` plus a trigger that makes a
  finished attempt immutable (`supabase/migrations/0009_company_assessments.sql`,
  tested on real Postgres via PGlite).
- The timer is server-authoritative. Saves are refused after the deadline; an
  attempt abandoned mid-test is finalised automatically with its last autosave.
- With Supabase configured, every API call must carry the user's Supabase
  access token (`Authorization: Bearer …`), so no one can start or submit an
  attempt for another student.

## Proctoring (parity with the original assessments)

`components/company/useProctoring.ts` + `ProctorOverlays.tsx`:

- pre-test gate: consent, **mandatory fullscreen**, external/mirrored display check;
- camera & microphone gate with live preview (continuing without a camera is
  allowed, as in the original assessments, but recorded);
- leaving the tab/window, exiting fullscreen or changing displays = warning;
  **3 warnings auto-submit**; connecting a display mid-test terminates;
- fullscreen lock with automatic re-entry; native permission prompts never count;
- identity **watermark** (name · CALIBIAI · attempt tag · company) over the test;
- right-click, copying question text, printing and dev-tools shortcuts blocked;
  pastes and screenshot keys logged;
- every event is autosaved to the attempt's proctoring log for reviewers.

## Scoring

- MCQs: 1 mark each, checked against the server-side key (no negative marking).
- Written: 10 marks × grader score. The grader zeroes empty, too-short,
  gibberish, repetitive or question-parroting answers before any model sees
  them; relevance (rubric coverage and density) gates credit for length and
  structure, so fluent off-topic answers score low. With
  `DEEPSEEK_API_KEY`/`CALIBIAI_API_KEY` set, an LLM grades against the rubric.
- Coding: 20 marks × tests passed, re-run on the server at submission. The
  item feedback carries a LeetCode-style verdict summary (e.g. `9/12 tests
  passed · stress 0/3 · 3 TLE`) and advice for time-outs, wrong answers and
  runtime errors.
- Round % → weighted overall score (0–100); sectional cut-offs drive the verdict
  (*Interview-ready*, *Almost there*, *Borderline*, *Not yet ready*).
- Candidates see round, section and area analytics plus written/coding feedback,
  never per-MCQ correctness (so the key cannot be reconstructed and shared).

## Coding rounds — a LeetCode-style judge

Every coding round is **LeetCode medium/hard** — there are no warm-up problems
in the pool (blueprint mixes: entry 80/20, service 60/40, medium 50/50,
product 30/70 medium/hard). The judge (`lib/company/codeRunner.ts`) runs the
candidate's function against:

- **sample tests** — the statement's examples; when one fails the candidate
  sees *their output vs the expected output*;
- **hidden tests** — edge cases; only pass/fail + timing is shown;
- **stress tests** — up to 10⁵ elements (e.g. an ascending histogram, a
  20,000-node chain listed backwards, a catastrophic-backtracking regex) that
  an O(n²)/exponential solution cannot finish.

Verdicts are per test: *passed*, *wrong answer*, *time limit exceeded*,
*runtime error*, with timings. Each test has its own limit (1 s by default;
stress tests 4 s in Python / 2 s in JavaScript), enforced with `SIGALRM` in
Python and `vm.runInThisContext` timeouts in Node (main context — a separate
vm context makes every `Math.*` lookup ~80× slower and would time out
efficient JavaScript). After two time-outs the remaining tests are skipped,
so an infinite loop costs seconds, not minutes.

**Fair on slow servers:** every run times a fixed micro-benchmark and scales
all limits by `measured / nominal` (clamped to 1–3×), so a busy host does not
time out correct solutions — naive solutions are 5–1000× slower and still fail.

**Deterministic inputs:** stress inputs are generator specs
(`{"$gen": "ints", "n": 100000, …}`) expanded by an xorshift PRNG implemented
identically in both languages (proven byte-identical by the tests); large
expected outputs are stored as sha256 digests of canonical JSON.

**Proof that the tests work** (`lib/__tests__/companyCoding.test.ts`, run by
`npm test`): every reference solution passes every test in **both**
languages; 38 deliberately naive solutions pass the samples but hit *Time
Limit Exceeded* on a stress test; wrong answers, crashes, syntax errors,
missing functions and infinite loops fail safely.

**Authoring:** problems live in `scripts/company-bank/coding/*.mjs` (statement,
tests, Python + JavaScript reference solutions, optional naive solutions).
`npm run compile:coding` runs both references through the real judge,
requires them to agree byte-for-byte on every output, fills in expected
values/digests, enforces that references use ≤ 40 % of each stress limit, and
writes `data/company/supplements/s03-coding.json`; then
`npm run build:company-bank`.

## Security of the answer key

`data/company/bank.json` is read from disk by `lib/company/bank.ts` (server
only) — never imported, so it cannot be bundled into client JavaScript.
`lib/__tests__/companySecurity.test.ts` fails the build if a client component
imports the bank or any server-only company module, and client payloads are
tested to contain no keys, rubrics or hidden tests.

## API

| Route | Purpose |
|---|---|
| `GET /api/company-assessments?student_id=` | dashboard statuses |
| `POST /api/company-assessments/start` | create or resume (409 when finished) |
| `GET /api/company-assessments/attempt` | resume view for the exam page (never creates) |
| `POST /api/company-assessments/save` | autosave answers + proctoring log |
| `POST /api/company-assessments/runtests` | hidden tests for a coding item in the caller's paper |
| `POST /api/company-assessments/submit` | final, idempotent, server-scored submission |
| `GET /api/company-assessments/result` | graded result (public projection) |

## Operations

- Apply `supabase/migrations/0009_company_assessments.sql`, then
  `0010_calibiai_average.sql` (both are also in `supabase/schema.sql`). Writes
  need `SUPABASE_SERVICE_ROLE_KEY`; without Supabase the local JSON store
  (`company_attempts`) is used.
- Company results count towards the student's CalibiAI Score (the average of
  every completed assessment) and appear in the admin console — see
  `docs/CALIBIAI_SCORE_AND_ADMIN.md`.
- Optional `COMPANY_PAPER_SECRET` salts paper seeds (falls back to
  `ADMIN_SECRET`).
- The code runner uses the same subprocess sandboxing caveats as the existing
  in-built compiler (see `lib/runTests.ts`).
